# 기능 설계 문서

## 1. 버드뷰

```
고객 ── 상품·브랜드 조회 / 좋아요 / 포인트 / 주문 ─┐
                                                 ├─ commerce-api ─→ DB
관리자 ── 브랜드·상품 CRUD / 재고 변경 / 주문 조회 ─┘   고객·관리자 API 구분
```

- **고객과 관리자의 API를 구분한다.** 같은 상품을 다루더라도 입력·권한·응답 필드가 다르다.
- **DB는 하나를 공유한다.** 관리자의 변경·삭제가 고객 조회에 바로 반영되어야 한다.

## 2. 도메인 관계

### 2.1 관계도

```
Brand 1 ── N Product ── 재고
User  1 ── N Like N ── 1 Product
User  1 ── N Order 1 ── N OrderItem ── 상품 식별자 · 수량 · 주문 시점 스냅샷(상품명·단가)
User  1 ── 1 Point ── 잔액
Order ── 품목 금액 합계 / 포인트 결제액 · 결제 결과
```

관계도의 선은 업무 관계를 나타낸다. 모든 선을 객체 참조로 구현하지 않고, 아래 기준으로 객체 참조와 식별자 보관을 나눈다.

### 2.2 참조 방식 판단 기준

| 질문 | 객체 참조 쪽 근거 | 식별자 보관 쪽 근거 |
|---|---|---|
| 상대의 상태가 그 객체의 **불변식**에 필요한가? (살아 있는 동안 계속 지켜야 하는가) | 객체가 스스로 지킴 | - |
| 유스케이스가 **시작될 때 한 번** 확인하면 되는가? | - | 확인하는 시점에만 조회하면 됨 |
| 함께 생성·변경·삭제되는가? | 한 덩어리로 움직임 | 각자 따로 수정·삭제됨 |
| 한쪽을 불러올 때 다른 쪽이 딸려 와도 되는가? | 항상 함께 필요함 | 딸려 오는 것이 부담임 |
| 누가 누구를 알아야 행동할 수 있는가? | 필요한 방향으로만 둠 | - |

"A가 없으면 B도 없다"는 생명주기에 대한 판단이다. 누가 누구를 참조할지는 "누가 누구의 상태를 알아야 규칙을 지키는가"로 따로 판단한다.

### 2.3 관계별 판단

| 관계 | 판단 | 근거 |
|---|---|---|
| Product → Brand | 객체 참조 | "브랜드 없이 존재할 수 없다"가 Product의 불변식임 |
| Like → User, Product | 둘 다 식별자 | Like의 불변식에 다른 객체의 상태가 필요하지 않음. 등록 시 상품 삭제 여부 확인(LIK-01)은 시작 시점의 한 번 확인임 |
| Order → OrderItem | Order가 품목을 앎 | 합계·상태 규칙을 Order가 지킴 |
| OrderItem → Order | 식별자 (`orderId`) | OrderItem이 Order의 상태로 판단할 규칙이 없음 |
| OrderItem → Product | 식별자 + 스냅샷 | 주문 시점의 값을 보존함 |
| Point → User | 식별자 (`userId`) | 잔액 규칙에 User의 상태가 필요하지 않음 |

#### Product → Brand: 객체 참조

- **근거:** "상품은 브랜드 없이 존재할 수 없다"는 Product의 불변식이다. 상품을 만들 때 Product가 `Brand` 를 받아 삭제되지 않은 브랜드인지 스스로 확인한다. 브랜드 확인을 빠뜨린 상품이 만들어질 수 없다. 식별자만 보관하면 이 확인을 application이 매번 빠뜨리지 않아야 한다.
- **보조 근거:** 상품은 반드시 하나의 브랜드에 속하고 수정해도 바뀌지 않는다. 생성자에서만 받고 변경 행동을 두지 않는다.
- **감수하는 비용**
  - Product 도메인 테스트마다 Brand 객체가 필요하다.
  - 생성 시점의 확인만 보장한다. 이후 브랜드가 삭제되는 경우는 브랜드 삭제 조건("삭제되지 않은 상품이 남은 브랜드는 삭제할 수 없다")이 막는다.
  - 상품 목록에서 N+1이 생길 수 있다. 다대일 관계라 페치 조인을 써도 페이징에 문제가 없다.
- **참고:** 상품 목록은 좋아요 수와 `likes_desc` 정렬 때문에 집계가 들어간 전용 조회가 될 가능성이 크다. 따라서 참조 방식은 목록 조회가 아니라 규칙을 기준으로 정한다.

#### Like → User, Product: 둘 다 식별자

- **근거:** Like는 사용자–상품 관계 자체만 표현한다. Like 자신의 규칙에는 User의 상태도 Product의 상태도 필요하지 않다.
  - 같은 사용자–상품 관계의 중복은 (`userId`, `productId`) 유니크 키로 막는다. (LIK-02)
  - 본인 관계만 취소하며, 상품이 삭제되었어도 취소할 수 있다. (LIK-03)
  - 좋아요 수는 관계에서 count로 조회한다.
  - "삭제된 상품에는 새 좋아요를 달 수 없다"(LIK-01)는 Product의 상태가 필요한 유스케이스의 협력이며, 등록 흐름에서 상품을 조회할 때 확인한다.
- **Product → Brand와의 차이:** 상품이 브랜드에 속한다는 것은 Product가 존재하는 동안 계속 지켜야 하는 불변식이라 Product가 Brand를 들고 스스로 지킨다. 반면 LIK-01은 좋아요를 **등록하는 시점에 한 번** 확인하면 되고, 등록된 뒤 상품이 삭제되어도 그 관계는 남는다(LIK-03). 확인하는 시점에만 Product를 조회하면 되므로 참조를 들 이유가 없다.
- **버린 대안:** Product를 객체로 참조한다. 내 좋아요 목록에서 상품 정보에 바로 접근할 수 있지만, 규칙이 아닌 조회 편의 때문에 참조가 생긴다. Product → Brand와 판단 기준이 어긋난다.
- **감수하는 비용:** 내 좋아요 목록에서 상품 정보를 따로 조회해 조합해야 한다.

#### Order → OrderItem: Order가 품목을 앎

- **근거:** "합계 = 품목 금액의 합"(ORD-05), "DRAFT에서만 확정"(ORD-07) 같은 규칙을 Order가 지킨다. 그러려면 Order가 자신의 품목을 알아야 한다.
  - 확정 시 재고 확인(ORD-10)에는 Order가 가진 품목별 총수량이 필요하지만, 재고는 Product가 가진다(2.4). Order 혼자 지킬 수 있는 규칙이 아니라 `domain/order` 의 `~Service` 가 조율한다(4.4).
- **OrderItem은 `orderId` 만 보관한다.** OrderItem이 Order의 상태를 보고 판단할 규칙이 없다.
  - 이번 범위의 주문 상태는 DRAFT·CONFIRMED뿐이고 주문 취소가 없다.
  - 품목을 수정하는 API가 없다.
  - 이후 품목 변경이 생기더라도 변경은 Order를 통해서만 하고, Order가 자신의 상태를 확인한다. OrderItem이 Order의 상태를 물어 스스로 막으면 규칙이 두 객체에 나뉜다.
- **JPA 매핑 방식은 구현할 때 정한다.** 단방향 `@OneToMany` + `@JoinColumn`, 양방향 `mappedBy`, 따로 저장 후 조율하는 방식 중에서 고른다.

#### OrderItem → Product: 식별자 + 주문 시점 스냅샷

- **근거:** 관리자가 상품의 이름·가격을 바꿔도 이미 만든 주문의 품목 정보와 금액은 바뀌지 않아야 한다. 주문 품목을 조회할 때 상품의 현재 상태 전체가 필요하지 않다.
- **스냅샷 시점:** DRAFT 생성 시점에 상품명·단가를 저장한다.
- **확정 시 가격 확인:** 확정할 때 스냅샷 단가와 상품의 현재 가격이 다르면 확정을 거절한다.
- **가격이 내려간 경우도 거절한다.** 오른 경우만 거절하면 내려간 가격을 스냅샷과 현재 가격 중 무엇으로 결제할지 추가로 정해야 한다. "다르면 거절"로 두어 고객이 본 금액과 결제 금액을 항상 같게 유지한다.
- **비교 대상은 단가뿐이다.** 상품명이 바뀌어도 결제 금액은 달라지지 않으므로 확정을 거절하지 않는다. 주문 품목에는 생성 시점의 상품명이 그대로 남는다.

| 대안 | 장점 | 비용 |
|---|---|---|
| **가격이 다르면 거절 (선택)** | 고객이 모르는 금액으로 결제되지 않음 | 그 DRAFT는 확정할 수 없어 고객이 주문을 새로 만들어야 함 |
| 현재 가격으로 결제하고 스냅샷 갱신 | 고객이 다시 주문하지 않아도 됨 | 생성 때 본 금액과 결제 금액이 달라짐 |
| 스냅샷 가격으로 결제 | 생성 때 본 금액 그대로 결제 | 관리자가 바꾼 가격이 반영되지 않음 |

- **확인 순서:** 가격·상품 삭제 여부·재고·잔액을 **모두 확인한 뒤** 재고·포인트를 차감한다. (ORD-08~ORD-11)
  - 트랜잭션이 롤백되면 DB 반영은 막을 수 있지만, 메모리의 도메인 객체는 이미 바뀐 상태로 남는다. 모두 확인한 뒤 변경하면 "거절 시 기존 값 유지"를 DB 없이 도메인 테스트로 확인할 수 있다.
  - 이론 문서의 "여러 품목이라면 전체 입력과 필요한 재고·잔액을 확인한 뒤 변경 행동을 호출합니다"와 같은 순서다.
  - 트랜잭션 롤백은 예상하지 못한 실패에서 DB 반영을 막는 보조 수단으로 둔다.
- **거절 후 상태:** 주문은 DRAFT로 남고 재고와 잔액은 바뀌지 않는다.

#### Point → User: 식별자

- **잔액만 저장한다.** 포인트 내역은 이번 범위의 요구가 아니다.
- **사용자 한 명에 Point는 하나다.** `userId` 유니크 키로 보장한다.
- **Point 행이 없으면 잔액은 0원이다.** 행은 첫 충전 때 만든다.
  - "행 없음"과 "잔액 0인 행"이 같은 의미가 되므로, 행이 없을 때 0원 Point로 바꾸는 일은 한 곳에서만 한다.
- **확장 가능성:** 충전·결제 이력이 필요해지면 포인트 내역을 별도로 둔다. 이때 잔액을 따로 저장할지 내역 합계로 계산할지 정해야 하고, 잔액을 따로 저장한다면 잔액과 내역 합계를 일치시킬 책임이 추가된다.
- **알려진 한계:** 첫 충전이 동시에 두 번 들어오면 둘 다 행이 없다고 보고 insert를 시도한다. 유니크 키가 데이터를 지키지만 한쪽 요청은 실패한다.

### 2.4 재고의 책임

**재고는 Product의 필드로 둔다.**

재고를 바꾸는 행동은 두 가지다.

| 행동 | 호출되는 경로 | 지키는 조건 |
|---|---|---|
| 차감 | 주문 확정 | 차감 수량은 양수, 보유량보다 많이 차감할 수 없음, 결과는 0 이상 (PRD-05, PRD-06) |
| 최종 수량 설정 | 관리자 재고 변경 | 삭제되지 않은 상품만, 결과는 0 이상 (PRD-04, PRD-05) |

#### 근거 ① 재고를 Product에 두는 이유

- **함께 생성·삭제되는가:** 그렇다. 재고는 상품 없이 존재하지 않고, 상품이 삭제되면 재고도 사용할 수 없다. 재고만 따로 생기거나 사라지는 경우가 없다.
- **규칙을 지키려면 상대의 상태를 알아야 하는가:** 그렇다. "삭제되지 않은 상품만 재고를 변경한다"(PRD-04)는 상품의 삭제 상태가 필요하다. 같은 객체에 두면 이 규칙이 자기 상태의 검사가 된다.
- **불러올 때 딸려 와도 되는가:** 그렇다. 재고는 숫자 하나이고, 상품을 조회할 때 재고를 얻으려고 추가 조회를 할 필요가 없다.
- **반론:** 변경 이유는 다르다. 이름·가격은 관리자 상품 수정에서, 재고는 주문 확정과 관리자 재고 변경에서 바뀐다. 응집도만 보면 분리할 근거가 된다.
- **그래도 두는 이유:** 이번 범위의 재고 규칙은 "0 이상", "보유량 이하 차감" 정도다. 분리해서 얻는 변경 격리보다 분리했을 때 생기는 비용이 크다.
  - 삭제 여부 확인이 객체 간 협력으로 바뀐다.
  - 상품 조회에 조인이 생긴다.
  - 두 엔티티의 생명주기(생성·삭제)를 맞춰야 한다.
  - 변경 이유가 다르다는 점은 감수하는 비용으로 남긴다.

#### 근거 ② 재고 규칙의 종류와 필드로 두는 이유

| 규칙 | 종류 | 적용되는 행동 |
|---|---|---|
| 재고는 0 이상 | 값의 유효성 | 차감, 최종 수량 설정 (결과 값에 공통 적용) |
| 차감 수량은 양수 | 행동의 입력 조건 | 차감 |
| 보유량보다 많이 차감할 수 없음 | 행동의 입력 조건 (요청 값과 현재 재고의 관계) | 차감 |

- 값의 유효성("0 이상")은 두 행동에 공통이므로, Product 안에서 재고를 바꾸는 행동이 공통으로 거치는 한 곳에서 검사해 중복을 막는다.
- **별도 값 객체로 감싸지 않는 이유:** 이론 문서의 도입 기준은 "의미가 혼동되거나 유효성 검사가 반복되는 곳"이다. 이번 범위에서는 규칙이 세 개이고 Product 안의 한 곳에 모을 수 있어 반복이 생기지 않는다.

#### 버린 대안과 비용

| 대안 | 얻을 수 있던 것 | 포기한 이유 |
|---|---|---|
| 별도 엔티티 (상품 식별자로 연결한 재고 테이블) | 이름·가격 수정과 재고 변경이 서로 다른 행을 바꾼다. 재고 규칙이 늘어나도 Product가 바뀌지 않는다. | 삭제되지 않은 상품만 재고 변경(PRD-04)이 Product 조회와 재고 변경의 협력으로 바뀐다. 상품 조회에 조인이나 추가 조회가 생긴다. 상품을 생성·삭제할 때 재고 행도 함께 생성·삭제해야 하고, 삭제 상태(`deletedAt`)가 두 곳에 생긴다. |
| 값 객체 (Product 안의 재고 타입, 같은 테이블) | 재고 규칙이 한 타입에 모인다. Brand 없이 재고 규칙만 단위 테스트할 수 있다. | 이번 범위의 재고 규칙은 세 개이고, Product 안의 한 곳에 모아 반복을 막을 수 있다. 타입과 JPA 매핑을 추가하는 비용에 비해 얻는 것이 작다. |

- **이 선택의 비용:** Product가 상품 정보(이름·가격·브랜드) 규칙과 재고 규칙을 함께 떠안는다. 상품 정보가 바뀌는 이유와 재고가 바뀌는 이유가 한 클래스에 모인다.

#### 반례 대입 결과

- **삭제된 상품의 재고 변경:** Product의 재고 변경 행동이 자신의 삭제 상태를 확인해 거절한다. 주인이 같으므로 다른 객체를 조회할 필요가 없다.
- **주문 확정의 재고 비교:** Order는 품목별 수량만 알고 재고는 모른다. Order 혼자서는 "재고 충분"(ORD-10)을 판단할 수 없다. 이 협력은 `domain/order` 의 `~Service` 가 조율한다(4.4).
- **테스트에 Brand가 필요한가:** 필요하다. Product가 생성할 때 Brand를 받으므로, 재고 규칙만 테스트할 때도 Brand를 먼저 만들어야 한다. 테스트용 Brand 생성을 한 곳(fixture)에 모아 비용을 줄인다. 값 객체였다면 없었을 비용이다.
- **동시 변경:** 재고와 이름·가격이 같은 행에 있다.
  - JPA(Hibernate)는 기본적으로 변경 감지 시 모든 컬럼을 UPDATE하므로, 관리자의 이름 수정이 그 사이에 확정된 재고 차감을 덮어쓸 수 있다.
  - 같은 상품을 동시에 확정하면 둘 다 같은 재고를 읽고 차감해 초과 판매가 생길 수 있다. 이 문제는 재고를 어디에 두든 생긴다.
  - 과제에 동시성 요구가 없으므로 이번 범위에서는 해결하지 않고 알려진 한계로 남긴다.

#### 다시 검토할 조건

- **재고 규칙이 늘어날 때** (예약 재고, 안전 재고, 입출고 이력) → 값 객체나 별도 엔티티로 분리를 검토한다.
- **동시성을 처리해야 할 때:** 재고를 잠그면 상품 행 전체가 잠겨 이름·가격 수정까지 막힌다. → 잠금 범위를 줄이기 위해 별도 엔티티를 검토한다.
- **재고가 상품 단위가 아니게 될 때** (옵션별, 창고별 재고) → 상품과 재고의 1:1 관계가 깨지므로 별도 엔티티가 필요하다.
- **재고 규칙 테스트에서 Brand를 준비하는 비용이 반복해서 문제가 될 때** → 값 객체를 검토한다.

#### 재고의 입력과 노출

- **상품 생성에서는 재고를 받지 않고 0으로 시작한다.** 재고는 `PUT /api-admin/v1/products/{productId}/stock` 으로만 바꾼다.
  - 재고를 설정하는 입구가 하나뿐이라 재고 규칙(PRD-04, PRD-05)을 한 경로에서만 지키면 된다.
  - **감수하는 비용:** 관리자가 상품을 팔려면 생성과 재고 설정을 두 번 호출해야 한다.
- **고객 응답에는 품절 여부만 내보내고, 수량은 관리자 응답에만 넣는다.**
  - 고객은 살 수 있는지만 알면 된다. 같은 상품이라도 고객과 관리자의 응답 필드가 다르다는 1장의 판단을 따른다.
  - 품절 여부(재고 0)를 판단해 응답을 만드는 일은 조회 결과의 구성이며 응답을 조합하는 쪽이 맡는다(3.1).

### 2.5 삭제 방식

**브랜드와 상품은 논리 삭제한다.** 행을 남기고 삭제 상태를 표시하며, 고객 조회와 새 주문에서 제외한다.

#### 근거

| # | 근거 | 물리 삭제였다면 |
|---|---|---|
| 1 | 삭제된 상품의 좋아요 관계를 본인이 취소할 수 있어야 한다 (LIK-03) | 상품 행이 사라질 때 좋아요 행을 함께 지울지 정해야 하고, 남기면 가리키는 대상이 없는 행이 된다 |
| 2 | 확정된 주문의 품목과 좋아요가 상품 식별자를 가리킨다 | 기존 참조가 깨진다 |
| 3 | 브랜드 삭제 조건이 "삭제되지 않은 상품(재고 0 포함)이 남으면 거절"이다 (BRD-02) | "삭제된 상품"이라는 상태가 없어 조건을 표현할 수 없다 |
| 4 | 관리자는 삭제된 상품이 포함된 과거 주문도 조회한다 | 주문 품목의 상품 식별자로 상품을 더 이상 찾을 수 없다 |

#### 감수하는 비용

- 고객 조회와 새 주문에서 삭제 상태 조건을 빠뜨리면 삭제된 대상이 노출된다. 조건을 빠뜨리지 않을 방법이 필요하다.
- 행이 남으므로 상품명 같은 값에 유니크 제약을 걸 때 삭제된 행까지 고려해야 한다.
- 삭제된 행이 쌓인다. 정리 기준은 이번 범위에서 정하지 않는다.

#### 삭제된 대상의 조회와 복원

- **삭제된 브랜드·상품은 관리자 목록에서도 제외한다.** 복원이 없으므로 목록에서 볼 이유가 적고, 고객·관리자 목록의 조회 조건이 하나로 통일된다.
  - **감수하는 비용:** 잘못 삭제한 대상을 관리자 화면에서 확인할 수 없다.
  - 관리자 주문 조회에서는 삭제된 상품이 포함된 과거 주문도 그대로 보인다. 주문 품목은 주문 시점 스냅샷을 쓴다(2.3).
- **복원 기능은 두지 않는다.** 과제 요구에 없다. BRD-02를 지켜야 하는 입구가 상품 생성과 브랜드 삭제 두 곳으로 유지된다.
  - 복원이 생기면 "삭제된 브랜드에 속한 상품의 복원"처럼 입구가 늘어난다. 그때 BRD-02의 표현을 다시 본다.

- **PRD-06과 ORD-10:** "보유량보다 많이 차감할 수 없음"은 Product 자신의 재고와 요청 수량의 비교라 자기 상태의 검사다. "모든 품목을 확인한 뒤 차감"은 Order의 총수량과 여러 Product의 재고가 필요해 유스케이스의 협력이다.

### 3.4 반례와 기대값

자기 상태의 검사 중 대표 규칙에 반례를 붙인다. 이 표가 도메인 단위 테스트의 입력과 기대값이 된다. 거절하는 경우 **기존 값이 유지되는지**까지 기대값에 포함한다.

| 규칙 ID | 반례 입력 | 기대 결과 |
|---|---|---|
| PRD-06 | 재고 5인 상품에 6 차감 | 거절하고 재고는 5로 유지된다 |
| PRD-06 | 재고 5인 상품에 0 또는 음수 차감 | 거절하고 재고는 5로 유지된다 |
| PRD-06 | 재고 5인 상품에 2 차감 | 재고가 3이 된다 (정상 사례) |
| PRD-05 | 관리자가 최종 재고를 음수로 설정 | 거절하고 기존 재고가 유지된다 |

| PNT-02 | 충전 후 잔액이 저장 타입의 표현 범위를 넘는 금액 | 거절하고 기존 잔액이 유지된다 |
| ORD-07 | CONFIRMED 주문을 다시 확정 | 거절하고 주문 상태·결제 정보가 그대로 유지된다 |
| ORD-09 | DRAFT 생성 후 상품 가격이 바뀐 상태에서 확정 | 거절하고 주문은 DRAFT로, 재고·잔액은 그대로 유지된다 |
| LIK-03 | 타인의 좋아요 관계를 취소 | 거절하고 관계가 남는다 |
| ORD-04 | 품목이 비어 있는 주문 생성 | 거절하고 주문이 만들어지지 않는다 |

- **TDD 대상으로 고를 대표 규칙:** PRD-06 (재고 차감). Red에서 "6 차감 거절 + 재고 5 유지"를 먼저 확인하고, 정상 사례(2 차감 → 3)를 함께 둔다. 정상 사례가 없으면 모든 요청을 거절하는 구현도 첫 테스트를 통과한다.
- 유스케이스의 협력에 속한 규칙(BRD-02, ORD-10, ORD-11 등)의 반례는 대표 흐름과 API 계약을 정한 뒤 그 절에 적는다.

## 4. 구조와 의존

스타터의 layer-first 구조와 명명을 따른다.

### 4.1 계층별 역할

| 계층 | 맡는 일 | 두는 것 | 직접 의존하지 않을 것 |
|---|---|---|---|
| `interfaces` | 고객·관리자의 입력과 응답 변환, 요청자 식별값 추출, 오류의 HTTP 매핑 | `~V1Controller`, `~V1Dto`, `~V1ApiSpec` | `infrastructure` |
| `application` | 유스케이스의 순서와 객체 협력 조율, 응답용 모델 구성 | `~Facade`, `~Info` | `interfaces`, `infrastructure` |
| `domain` | 상태와 규칙, 여러 객체가 얽힌 업무 판단, 필요한 저장 약속 | 엔티티, `~Service`, `~Repository`(인터페이스) | `interfaces`, `application`, `infrastructure` |
| `infrastructure` | 저장 약속의 JPA 구현 | `~RepositoryImpl`, `~JpaRepository` | HTTP 응답 정책, 중복된 업무 규칙 |

`ArchitectureTest` 가 이 의존 방향을 검사한다.

### 4.2 이름 규칙

`application` 과 `domain` 모두에 조율하는 클래스가 있으므로 패키지와 접미사로 구분한다.

| 위치 | 접미사 | 하는 일 |
|---|---|---|
| `application/<기능>` | `~Facade` | 이론 문서의 애플리케이션 서비스. 모델 조회 → 행동 호출 → 저장 → 결과 구성 |
| `domain/<기능>` | `~Service` | 한 엔티티에 자연스럽게 속하지 않는 업무 판단 |

### 4.3 패키지 배치

```
interfaces/api/product        → application/product → domain/product
interfaces/api/admin/product  → application/product → domain/product
infrastructure/product        ─────────────────────→ domain/product
```

- 기능 단위는 `brand`, `product`, `like`, `point`, `order` 로 나눈다.
- 고객 API와 관리자 API는 `interfaces` 에서 갈라진다. 같은 저장된 상품을 쓰더라도 입력·출력 모델이 다르다(1장).

### 4.4 기존 패키지를 따르는 선택

- **저장 약속은 `domain` 의 인터페이스, 구현은 `infrastructure`.** `application` 은 구현체 이름을 모른다. 테스트에서는 DB 없이 fake 구현을 연결할 수 있다.
- **`domain` 의 `~Service` 가 조회·저장과 대상 없음 예외를 맡고, `~Facade` 는 조율과 결과 구성을 맡는다.** 스타터의 `ExampleService` · `ExampleFacade` 와 같은 분담이다.
- **트랜잭션 경계는 스타터와 같이 `domain` 의 `~Service` 에 둔다.**
- **여러 객체에 걸친 협력은 `domain` 의 `~Service` 가 조율한다.** 주문 확정(ORD-06~ORD-12)이 여기에 해당한다.
  - 서비스는 저장 약속을 통해 필요한 모델을 조회하고, 모두 확인한 뒤 각 객체의 행동을 호출한다. 스타터의 `ExampleService` 와 같은 모양이며 트랜잭션 경계가 이 서비스에 그대로 유지된다.
  - **차감은 각 객체가 한다.** 서비스는 `product` 와 `point` 에 행동을 요청하고, 수량·잔액의 조건은 각 객체가 판단한다(PRD-06, PNT-03). 서비스가 값을 꺼내 비교하고 다시 넣지 않는다.
  - **버린 대안 ①** `~Facade` 가 조율한다. 유스케이스 순서가 한곳에 보이지만 업무 규칙인 재고·잔액 확인이 application에 자리하고, 트랜잭션 경계를 Facade로 올려야 한다.
  - **버린 대안 ②** 서비스는 판단만 하고 조회·저장은 `~Facade` 가 맡는다. DB 없이 확정 규칙을 테스트할 수 있지만 트랜잭션 경계가 Facade로 올라가고 스타터와 모양이 달라진다.
  - **버린 대안 ③** `Order` 가 상품·포인트를 받아 직접 차감한다. 이론 문서의 "상품이 사용자 잔액까지 직접 변경하지 않는다" 와 어긋난다.
  - **감수하는 비용:** `domain/order` 의 서비스가 `domain/product` · `domain/point` 의 저장 약속을 알게 된다. 확정 규칙을 테스트하려면 fake 구현이 필요하다.
- **업무 오류 코드를 따로 둔다.** 1주차 결정 1을 이어간다. `domain` 에서 생긴 실패마다 고유한 업무 오류 코드를 붙이고, 그 코드를 HTTP 상태로 바꾸는 일은 `interfaces` 의 변환 지점(`ApiControllerAdvice`)에서 한다.
  - **이유:** 스타터의 `ErrorType` 만 쓰면 "없는 주문"과 "매핑되지 않은 경로"가 같은 404·같은 코드가 된다. 요청자가 주문을 다시 찾아야 할지 쿠폰·상품을 바꿔야 할지 고를 수 없어 메시지 문자열로 분기하게 된다.
  - **감수하는 비용:** 코드 목록을 관리해야 하고, 새 실패를 추가할 때 기존 코드와 의미가 겹치지 않는지 확인해야 한다.
  - 기존 `ErrorType` 을 확장할지 업무 코드 타입을 따로 둘지는 구현할 때 정한다.
- **엔티티는 `interfaces` 로 나가지 않는다.** `application` 이 `~Info` 로 바꾸고, `interfaces` 가 응답 모델로 바꾼다.
- **엔티티는 `modules:jpa` 의 `BaseEntity` 를 상속한다.** `domain` 에 JPA 애노테이션이 들어오지만 이번 범위에서는 그대로 둔다.
  - `BaseEntity` 의 `deletedAt` 과 멱등한 `delete()` 가 2.5의 논리 삭제 결정에 그대로 쓰인다.
  - 저장 전용 모델을 따로 두면 경계는 엄격해지지만 모델 간 변환과 관리 비용이 생긴다. 패키지 의존 규칙을 지키는 일과 프레임워크를 걷어내는 일은 다른 선택이다.

### 4.5 아직 정하지 않은 것

| # | 질문 | 답에 따라 달라지는 것 |
|---|---|---|
| Q-3 | 상품 목록의 조회 전용 모델(브랜드 정보 + 좋아요 수 집계 + `likes_desc` 정렬)을 어디에 두는가 | `domain` 의 저장 약속이 반환하는 타입. 조회를 조합하는 위치 |
| Q-4 | 요청자를 조건으로 거는 규칙(ORD-06, LIK-03)을 소유자까지 조건으로 건 조회로 처리하는가 | "없음"과 "타인 것"이 같은 응답이 되는지 (1주차 INV-001의 방식) |

## 5. 대표 흐름: 포인트 충전 → 주문 확정

고객이 포인트를 충전하고, 주문을 만들고, 확정해 결제하는 흐름이다. 여러 객체가 협력하는 흐름이라 대표로 고른다.

**이 문서에서 "확정(confirm)"은 결제를 마치는 것을 뜻한다.** 수령 후의 구매확정과는 다르다. 이번 범위의 주문 상태는 DRAFT·CONFIRMED뿐이고 배송·취소·환불은 없다.

### 5.1 연결 흐름

```
POST /api/v1/points/charge        10,000 충전  → 잔액 10,000
POST /api/v1/orders               DRAFT 생성   → 합계 7,000 (차감 없음)
POST /api/v1/orders/{id}/confirm  확정·결제    → 재고 차감, 포인트 7,000 차감
GET  /api/v1/points               잔액 조회    → 3,000
GET  /api/v1/orders/{id}          주문 조회    → 품목·금액·상태·결제액
```

### 5.2 주문 생성 (DRAFT)

```
생성 요청 → [요청자 식별]              interfaces
          → 상품들 조회                 domain/order 의 ~Service
          → [확인] ORD-01, ORD-02, ORD-04
          → 같은 상품 품목 합산          ORD-03
          → 스냅샷(상품명·단가) 저장
          → [합계 계산] ORD-05
          → DRAFT 저장 → OrderInfo 구성  ~Facade
```

- **차감하지 않는다.** 재고와 포인트는 확정할 때만 움직인다.
- **같은 상품의 품목은 저장할 때 합친다.** 요청이 두 줄이어도 주문에는 한 품목으로 남는다. 이후의 합계·가격 비교·재고 차감이 상품별로 유일한 품목을 다루게 된다.
  - **버린 대안:** 요청한 모양대로 저장하고 재고 확인만 총수량으로 한다. 요청이 그대로 보이지만 합계·가격 비교·차감이 매번 상품별로 모아 계산해야 한다.
  - **감수하는 비용:** 고객이 보낸 품목 수와 주문 조회의 품목 수가 다를 수 있다.
- 같은 상품이므로 합산한 품목의 단가는 하나로 정해진다. 스냅샷은 같은 시점에 찍힌다.

### 5.3 주문 확정 (CONFIRMED)

조율은 `domain/order` 의 `~Service` 가 맡는다(4.4).

```
확정 요청 → [요청자 식별]                      interfaces
          → 주문 조회 · 상품들 조회 · 포인트 조회   domain/order 의 ~Service
          ── 확인 단계 ────────────────────────
          → 본인 주문인가            ORD-06
          → DRAFT 인가              ORD-07
          → 상품이 삭제되지 않았나     ORD-08
          → 스냅샷 단가 = 현재 가격?  ORD-09
          → 재고가 충분한가           ORD-10
          → 잔액이 결제액 이상인가     ORD-11
          ── 변경 단계 ────────────────────────
          → product.재고차감(수량)    PRD-06   각 객체가 조건을 판단함
          → point.결제(결제액)        PNT-03
          → order.확정(결제 정보)     ORD-12
          → 저장 → OrderInfo 구성      ~Facade
```

- **모두 확인한 뒤 모두 변경한다.** 차감 뒤에 불일치를 발견하면 되돌려야 한다(2.3).
- **확인 순서는 위 순서로 고정한다.** 재고와 잔액이 둘 다 부족하면 **재고 부족**을 알린다.
- **여러 품목의 재고가 부족하면 품목 순서대로 처음 실패한 상품을 알린다.** 순서를 정해 두어야 기대값이 흔들리지 않는다.
- **차감은 각 객체가 한다.** 서비스는 수량·결제액을 넘겨 행동을 요청하고, 조건 판단은 Product와 Point가 한다.
- **포인트 행이 없으면 잔액 0원으로 본다**(2.3). 충전한 적이 없는 고객의 확정은 잔액 부족으로 거절된다.

### 5.4 실패 지점과 유지되는 것

| 실패 | 규칙 | 유지되는 것 |
|---|---|---|
| 타인의 주문 확정 | ORD-06 | 주문 상태·재고·잔액 그대로 |
| 이미 확정된 주문 | ORD-07 | 기존 결제 정보 그대로 |
| 삭제된 상품 포함 | ORD-08 | DRAFT 유지, 재고·잔액 그대로 |
| 가격이 달라짐 | ORD-09 | DRAFT 유지, 재고·잔액 그대로 |
| 재고 부족 | ORD-10 | DRAFT 유지, 재고·잔액 그대로 |
| 잔액 부족 | ORD-11 | DRAFT 유지, 재고·잔액 그대로 |

확인 단계에서 거절하므로 어떤 실패에서도 재고와 잔액이 바뀌지 않는다. 확인과 변경을 나눈 이유가 이 표다.

### 5.5 확정할 때 저장하는 것

| 값 | 저장하는 이유 |
|---|---|
| 결제액 | 합계는 주문을 만든 시점의 금액이고 결제액은 실제로 차감한 금액이다. 지금은 값이 같지만 할인이 붙으면 갈라진다 |
| 결제 시각 | `BaseEntity.updatedAt` 은 이후 변경으로 덮인다. 언제 결제됐는지는 덮이면 안 되는 값이므로 별도로 둔다 |
| 결제 결과 | 별도 필드를 두지 않고 **주문 상태가 대신한다.** 결제가 실패하면 확정 자체가 거절되므로 저장된 주문에는 성공만 남는다 |

- **결제 수단은 포인트뿐이다.** 수단이 늘어나면 결제 결과를 따로 담을지 다시 검토한다.

- **품목이 비어 있는 주문은 거절한다**(ORD-04). 합계 0원 주문을 확정해도 재고·잔액이 바뀌지 않아 결제로서 의미가 없다. 빈 주문이 만들어지지 않으므로 확정 단계에서 품목이 없는 경우를 다루지 않아도 된다.
