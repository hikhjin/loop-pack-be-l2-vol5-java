# 쿠폰 할인 적용 설계 문서

## 1. 기준 문장

> **"구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고, 확정된 할인 금액은 나중에 바뀌지 않아야 합니다."**

---

## 2. 사실, 조건, 질문

### 2.1 확인된 제품 약속

기준 문장에서 근거를 가리킬 수 있는가?

| # | 내용                                                                    | 근거 |
|---|-----------------------------------------------------------------------|---|
| F-1 | 쿠폰을 적용하는 주체는 그 주문을 소유한 구매자이고 쿠폰도 해당 구매자가 보유한 것이며, 주문 확정 전에만 적용할 수 있다. | 기준 문장의 "구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고" |
| F-2 | 확정된 할인 금액은 이후 정책이나 가격이 바뀌어도 변하지 않는다.                                  | 기준 문장의 "확정된 할인 금액은 나중에 바뀌지 않아야 한다" |


### 2.2 실습 장면의 조건

실제 제품으로 일반화하면 안 된다. 복수 쿠폰, 운영자 강제 할인, 환불·정산과 결합되면 달라지기 때문이다.

| # | 내용                         |
|---|----------------------------|
| C-1 | 한 주문에는 쿠폰 한 장만 적용한다. |
| C-2 | 할인액은 0원부터 주문 원금 사이여야 한다. |
| C-3 | 같은 주문·쿠폰 재요청은 첫 결과를 그대로 돌려준다. |
| C-4 | 쿠폰 만료 여부는 요청을 받은 시각으로 판단한다. |


### 2.3 제품 담당자에게 물어야 할 질문

답에 따라 사용자 응답, 저장 데이터, 권한이 달라지는가?

| # | 질문 | 답에 따라 달라지는 것 |
|---|---|---|
| Q-1 | 운영자도 타인의 주문에 쿠폰을 적용할 수 있는가? | **권한.** 소유권 규칙 `INV-001` 의 주체가 바뀌고 감사 기록이 필요해진다. |
| Q-2 | 쿠폰 할인액이 주문 원금을 넘으면 원금까지 잘라서 적용하는가, 아니면 거절하는가? | **저장 데이터.** 확정 할인액에 원금이 저장될지 요청이 실패할지가 갈린다. |
| Q-3 | 같은 주문·쿠폰 재요청은 성공 응답인가, 이미 적용되었음을 알리는 실패인가? | **사용자 응답.** `C-3` 은 결과 재사용까지만 정했고 외부 표현은 비어 있다. |
| Q-4 | 쿠폰은 적용 시점에 소비되는가, 주문 확정 시점에 소비되는가? 적용 후 주문이 취소되면 복구되는가? | **저장 데이터.** 쿠폰 상태 전이와 복구 이력의 유무가 갈린다. |
| Q-5 | 확정 전 주문의 상품 가격이 바뀌면 이미 적용된 할인은 재계산되는가? | **사용자 응답.** 재계산이면 확정 전 조회 금액이 요청마다 달라진다. `F-2` 는 확정 이후만 약속한다. |

## 3. 사용 장면 (참고용)

```
Use case UC-01: 주문에 쿠폰 적용
주 사용자: 구매자
시작 조건: 요청자가 소유한 주문이며 아직 확정되지 않음
시작 사건: 보유 쿠폰 중 couponId 를 골라 적용을 요청
성공 결과: 할인 결과가 기록되고 최종 주문 금액이 반환됨
실패 결과: 주문 없음 / 소유자 다름 / 주문 확정됨 / 쿠폰 사용 불가
종료 조건: 성공한 할인 결과는 이후 정책·가격 변화에도 동일
```

## 6. 외부 계약

| 항목 | 값                                                                           |
|---|-----------------------------------------------------------------------------|
| method · path | `POST /api/v1/orders/{orderId}/discount`                                    |
| 사용자 식별 | `X-USER-ID` 헤더                                                              |
| 요청 본문 | `{ "couponId": <long> }`                                                    |
| 성공 | `200`, `data`: `orderId`, `originalAmount`, `discountAmount`, `finalAmount` |


| 상황 | HTTP status | `errorCode`               | 관련 규칙 |
|---|-------------|---------------------------|---|
| 주문 없음 또는 타인의 주문 | 404         | `ORDER_NOT_FOUND`         | INV-001 |
| 쿠폰 없음 또는 타인의 쿠폰 | 404         | `COUPON_NOT_FOUND`        | INV-002 |
| 주문이 이미 확정됨 | 409         | `ORDER_ALREADY_CONFIRMED` | INV-004 |
| 이미 다른 쿠폰이 적용됨 | 409         | `COUPON_ALREADY_APPLIED`  | INV-002 |
| 쿠폰 만료 또는 사용 불가 | 409         | `COUPON_NOT_USABLE`       | INV-006 |
| `couponId` 누락 또는 형식 오류 | 400         | `BAD_REQUEST`             | - |

타인의 주문이나 쿠폰의 존재 여부를 노출하지 않기 위해 소유자 다름을 별도 코드로 나누지 않고 없음과 합친다.

## 7. 설계 결정 및 버린 대안

### 결정 1 · 실패를 업무 오류 코드로 구분한다

- **선택** 도메인에서 생긴 실패마다 고유한 업무 오류 코드를 붙이고, 그 코드를 HTTP 상태로 바꾸는 일은 따로 떼어 둔 변환 지점에서 처리한다. 요청자는 상태 코드 뿐만 아니라 `COUPON_NOT_USABLE` 같은 코드를 읽고 다음에 무엇을 할지 정한다.
- **버린 대안** 지금 있는 `ErrorType` 의 네 값을 그대로 쓰고 차이는 메시지 문구로만 표현한다.
- **버린 이유** 현재 존재하지 않는 대상과 매핑되지 않은 경로가 이미 같은 404와 같은 코드로 응답하고 있다. 이대로 두면 클라이언트는 실패를 받고도 주문을 다시 찾아야 할지 쿠폰을 바꿔야 할지 다음 행동을 고를 수 없어 메시지 문자열로 분기하는 코드를 짜게 된다. 그런 코드는 메세지 문구를 수정하거나 다국어를 붙이는 순간 깨진다.
- **또 다른 대안** 불변식마다 예외 클래스를 하나씩 만든다. 어떤 규칙이 깨져서 실패했는지 타입만 봐도 알 수 있다는 장점이 있다. 다만 규칙이 늘어날 때마다 클래스가 같이 늘어나 유지보수 비용이 증가한다.
- **감수하는 비용** 코드 목록을 누군가 관리해야 하고, 새 실패를 추가할 때 기존 코드와 의미가 겹치지 않는지 확인해야 한다.

### 결정 2 · 확정된 할인은 스냅샷으로 고정한다

- **선택** 쿠폰 적용이 성공한 시점의 원금과 할인액과 최종 금액을 주문 정보에 함께 저장한다.
- **버린 대안** 주문을 조회할 때마다 현재 정책으로 할인을 다시 계산한다. 저장할 값이 줄고 정책을 바꾸면 곧바로 반영된다는 장점이 있다. 화면에서 사용자가 보고 싶은 것은 지금 이 순간의 가격이기 때문이다.
- **버린 이유** 확정된 주문에서 이 방식을 버린 근거는 `INV-004` 때문이다. 할인율을 10%에서 20%로 바꾸는 순간 이미 결제가 끝난 과거 주문의 금액까지 따라 움직인다. 이는 제품이 한 약속을 어기는 일이다. 확정 전 주문이 둘 중 어느 쪽을 따라야 하는지는 아직 열려 있고, `Q-5` 의 답변을 들어야 한다.
- **감수하는 비용** 스냅샷을 누가 언제 만드는지 정해야 한다. 확정 전 금액과 확정 후 금액이 서로 다른 경로로 계산되므로 두 경로가 같은 계산식을 쓰는지 테스트로 묶어 두어야 한다.

### 결정 3 · 할인 적용 순서를 주문 객체 안에 숨긴다

- **선택** 쿠폰을 적용하려면 쿠폰 사용 가능 여부를 확인하고, 할인 금액을 계산하고, 그 결과를 스냅샷으로 고정하고, 주문 총액을 다시 맞춰야 한다. 이 네 단계를 주문 객체가 가진 메서드 하나 안에서 처리한다. 바깥에서 하는 일은 쿠폰과 요청 시각을 넘기며 쿠폰 적용 요청만 하면 된다.
- **버린 대안** 응용 계층이 가격 조회, 쿠폰 조회, 검증, 할인 계산, 총액 재계산을 직접 순서대로 늘어놓는다. 각 단계가 눈에 보여서 파악하기 쉽다.
- **버린 이유** 쿠폰 적용부터 주문 저장까지의 순서를 바깥이 알아야 한다는 점이 문제다. 쿠폰이 한 장만 적용된다는 규칙과 금액 범위 규칙을 호출하는 곳마다 다시 지켜야 하고, 호출 지점이 늘어날수록 빠뜨리는 자리도 늘어나 유지보수 비용이 커진다.
- **감추는 변경 이유** 할인을 어떻게 계산하는지가 바뀌는 경우와, 쿠폰을 쓸 수 있는지 판단하는 기준이 바뀌는 경우 등 모두 주문 객체 안에서만 고치면 끝난다.
- **감수하는 비용** 해당 방식은 주문 객체 자체를 무겁게 만든다. 감추는 결정보다 바깥에 드러나는 개념이 더 많아지기 시작할 경우, 경계를 다시 나눠야 하는지 확인이 필요하다.
