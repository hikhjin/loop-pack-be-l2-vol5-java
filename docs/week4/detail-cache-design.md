# 상품 상세 캐시 설계

Redis cache-aside 를 상품 상세(`GET /api/v1/products/{productId}`)에 붙인다. 목록 캐시(`cache-design.md`)와 같은 버전 방식을 쓰고, 다른 점만 이 문서에 적는다.

## 1. 왜 상세도 캐시하나

`cache-design.md` 1절은 상세의 원본 비용이 작아(p50 약 2.8ms) 캐시하지 않기로 했다. 이번에는 다음 두 가지 때문에 다시 판단한다.

- **목표: 조회 성능을 최대한 높인다.** 2.8ms 중 약 1.5~2ms는 SQL 이 아니라 커넥션 획득 · 트랜잭션 · DB 왕복 비용이다(`product-query-cache.md` 관찰 4). hit 는 이 비용을 통째로 없앤다.
- **가정: 인기 상품에 트래픽이 몰린다.** 3주차 실험에서 몰릴 때의 병목은 커넥션 풀이었다(`../week3/experiment-stock-strategy.md` 관찰 3). hit 는 커넥션을 잡지 않는다.

이득의 크기(hit 지연)는 측정으로 확인한다(8절).

## 2. 키와 저장 내용

| 항목 | 값 |
|---|---|
| 데이터 키 | `product-detail:v1:{productId}:ver={상품 버전}`. `v1` 은 저장 형식 버전 |
| 버전 키 | `product-detail:version:{productId}`. TTL 없음 |
| 저장 내용 | `{"view": ProductView}` (JSON). 상품이 없거나 삭제됐으면 `{"view": null}` ("없음") |
| TTL | 데이터 키 60초 (`product-detail-cache.ttl-seconds`). 목록과 같은 값이지만 설정은 따로 둔다 |

- `ProductView` 는 재고 수량을 담지만 고객 응답은 품절 여부만 내보낸다(2주차 2.4). 그래서 무효화는 품절 여부가 바뀔 때만 한다(3절).
- 사용자별 필드가 응답에 없어 공용 캐시에 섞일 정보가 없다.

## 3. 무효화

### 3.1 상품별 버전을 올린다

| 후보 | 판단 |
|---|---|
| A. 키 삭제 | 읽기가 Redis 왕복 1회로 가장 빠르다. 그러나 변경 전에 DB 를 읽은 조회가 삭제 *뒤에* 옛 값을 저장하면(늦은 채움) TTL 까지 옛 가격 · 옛 품절이 남는다 |
| B. 키 삭제 + 지연 재삭제 | 늦은 채움을 줄이지만 없애지 못한다(지연보다 늦게 저장하는 요청). 재삭제 예약이 필요하고, 인기 상품 키가 한 번 더 사라진다 |
| C. 상품별 버전 (왕복 2회) | 늦은 채움은 *옛 버전 키*에만 들어간다. 목록과 같은 방식이라 버전 생성(`cache-design.md` 3.5) · 실패 재처리(3.4) · master 읽기(4.1)를 그대로 따른다. 대가: hit 마다 버전 · 데이터를 따로 읽어 왕복 2회, 버전 키가 무효화된 상품 수만큼 남음. **처음 구현했으나 측정 뒤 아래로 바꿨다** |
| **C + Lua (채택)** | C 와 키 · 저장 형식 · 무효화가 같고, 버전 · 데이터를 스크립트 한 번(`VersionedCacheScript`)으로 읽어 왕복이 1회다. MockMvc 기준 hit p50 이 C 보다 약 0.35~0.42ms(C hit 의 약 35~40%) 짧았다(`product-detail-cache.md`). master 요청 수는 C 와 같다(hit 마다 1회). 대가: 스크립트 관리, 목록 캐시(왕복 2회)와 읽기 방식이 다름, 데이터까지 master 에서 읽음(상세 값은 약 150 bytes 라 송출 부담이 작다), Cluster 전환 때 해시 태그 필요(9절) |

채택 근거: 가격과 품절 여부는 정상 상황에서 최신이어야 한다(5절). 늦은 채움이 생기면 키 하나에 든 값이 모두 옛 값이 되므로, 가격만 따로 지킬 수 없다. 그래서 버전 방식(C)을 쓰고, 조회 성능을 최대한 높이는 목표(1절)에 따라 읽기를 스크립트 한 번으로 줄였다.

- **목록 캐시도 뒤이어 같은 방식으로 바꿨다.** 목록 첫 페이지는 약 3KB 라 데이터까지 master 가 보내는 부담이 상세보다 크므로, 값 크기와 hit 지연을 따로 잰 뒤 정했다(`product-list-cache-lua.md`, `cache-design.md` 4.1). 같은 스크립트를 접미사(`:sort=…`)만 바꿔 쓴다.

### 3.2 무효화하는 쓰기

| 쓰기 | 위치 | 상세 무효화 |
|---|---|---|
| 상품 생성 | `AdminProductFacade` | **새 상품 ID.** "없음" 캐시 때문에 필요하다(3.3) |
| 상품 수정 · 삭제 | `AdminProductFacade` | 그 상품 |
| 관리자 재고 변경 — 품절 여부가 뒤집힐 때만 | `AdminProductFacade` | 그 상품 |
| 주문 확정의 재고 차감 — 품절이 된 상품만 | `OrderFacade` | 품절이 된 상품들 |
| 브랜드 수정 · 일괄 삭제 | — | **하지 않는다.** 브랜드명 · 삭제된 상품 노출은 TTL 동안 허용한다(5절) |
| 좋아요 등록 · 취소 | — | **하지 않는다.** 좋아요 수는 TTL 동안 오래될 수 있다(5절) |

- 무효화 호출은 목록 캐시와 같은 자리에 둔다. 쓰기 경로가 명시적으로 부르고, 진행 중인 트랜잭션이 있으면 commit 뒤로 미룬다(`cache-design.md` 3.4).
- **버린 대안: 브랜드 삭제 때 그 브랜드의 상품 ID 를 조회해 모두 무효화한다.** 브랜드 행 잠금 덕에 조회한 ID 와 지운 상품이 일치하고 조회 비용도 작다. 그러나 큰 브랜드는 무효화 대상이 수만 개가 되고 실패 재처리 기록도 그만큼 커진다. 삭제된 상품은 주문 확정에서 DB 가 막으므로(영향은 "보였는데 주문이 안 됨") TTL 동안 노출을 허용하는 쪽을 골랐다.
- 좋아요를 무효화하지 않는 또 하나의 이유: 인기 상품일수록 좋아요가 잦아, 무효화하면 인기 상품 키가 계속 사라져 동시 miss 가 생기기 쉬운 조건이 된다.

### 3.3 "없음"도 캐시한다

- 없는 상품 · 삭제된 상품의 조회도 `{"view": null}` 로 저장하고, hit 면 DB 를 거치지 않고 `PRODUCT_NOT_FOUND`(404)로 끝난다.
- 이유: 삭제된 인기 상품이나 오래된 링크로 오는 같은 ID 의 반복 요청이 매번 DB 로 가면, 요청마다 커넥션을 잡는다.
- 대가 1: **상품 생성 때 새 ID 를 무효화해야 한다.** 아직 없는 ID 를 먼저 조회해 "없음"이 저장된 뒤 그 ID 로 상품이 생기면, TTL 동안 404 가 나간다.
- 대가 2: "없음"을 나타내는 저장 형식이 필요하다(2절).

| 후보 | 판단 |
|---|---|
| **캐시함 (채택)** | 같은 없는 ID 의 반복 요청은 TTL 마다 DB 1회 |
| 캐시하지 않음 | 생성 시 무효화 · 빈 값 형식이 필요 없다. 그러나 404 요청은 모두 DB 로 가고, Redis 확인 비용까지 더해진다 |

### 3.4 "없음"을 캐시에 넘기는 방식

조회 결과를 `Optional<ProductView>` 로 받는다. `ProductService.findActiveProductView` 가 살아 있는 상품만 돌려주고, 상세 조회의 404 는 `ProductFacade` 가 같은 `PRODUCT_NOT_FOUND` 로 던진다. 외부 계약(404 · 오류 코드)은 바뀌지 않는다.

| 후보 | 판단 |
|---|---|
| **`Optional` 로 받고 호출자가 예외를 정함 (채택)** | 캐시가 "없음"을 값으로 다룬다. 대가: 2주차 설계 4.4 의 "대상 없음 오류도 호출된 서비스가 던진다"에서 **상세 조회만 벗어난다.** 다른 유스케이스(좋아요 · 주문)는 그대로 `ProductService` 가 던진다 |
| 캐시 구현이 `PRODUCT_NOT_FOUND` 예외를 잡아 "없음"으로 저장 | 서비스 · Facade 는 그대로다. 그러나 인프라가 도메인 예외의 의미를 해석하게 되고, 2주차 4.4 의 "공유된 예외를 잡아 다른 예외로 바꾸지 않는다"와 어긋난다 |

- 2주차 4.4 가 적어 둔 "다시 검토할 조건"은 유스케이스마다 **오류가 달라질 때**다. 이번에는 오류가 같고, 캐시가 "없음"을 값으로 다뤄야 한다는 **다른 이유**로 바꾼다. 4.4 의 조건을 넓혀 적는다.

### 3.5 실패와 버전 키

- `INCR` 실패: 쓰기 응답은 성공이다. 실패한 **상품 ID** 를 메모리 집합에 기록하고 몇 초 간격으로 다시 올린다(`cache-design.md` 3.4 와 같음). 앱이 재시작되면 기록을 잃고 TTL 이 남은 오차를 막는다.
- 버전 키가 없으면 현재 시각(ms)으로 `SETNX` 해 만든다(`cache-design.md` 3.5 와 같음).

## 4. 읽기

```
ProductFacade.getProduct (트랜잭션 없음)
  1. 스크립트 한 번으로 버전과 그 버전의 데이터 읽기 (master)
     ─ 버전 키가 없으면 스크립트 안에서 현재 시각으로 만든다
     ─ 실패하면 → DB, 캐시에 쓰지 않음
  2. 데이터가 있으면 view 또는 "없음" 반환 ─ 값을 읽을 수 없으면 → DB, 캐시에 쓰지 않음
  3. miss → DB 조회 (여기서 읽기 트랜잭션 시작)
  4. 1에서 읽은 버전의 데이터 키에 TTL 과 함께 저장 ─ 실패해도 결과는 반환
  5. view 가 없으면 PRODUCT_NOT_FOUND
```

- 버전을 master 에서 읽는 이유와 "버전 읽기 → 트랜잭션 시작" 순서는 `cache-design.md` 4.1 과 같다. 데이터도 같은 스크립트 안에서 읽으므로 master 에서 읽는다. replica 로 읽기를 나누지 않는다.
- Redis 연결은 목록 캐시의 연결(`ProductCacheRedisConfig`, 대기 한도 100ms)을 함께 쓴다. Redis 오류는 miss 와 구분해 기록하고 DB 로 우회한다(4.2 와 같음).

## 5. 허용 신선도

| 데이터 | 정상 상황 (변경 완료 뒤 시작한 순차 조회) | 장애 · 경쟁 |
|---|---|---|
| 가격 · 이름 · 품절 여부 · 상품 생성 | 최신 (3.2 무효화) | `INCR` 실패 시 재처리까지, 최대 TTL 60초 |
| 단건 상품 삭제 | 최신 (404) | 위와 같음 |
| 브랜드명 · 브랜드 삭제로 지워진 상품 | 최대 TTL 60초 오래될 수 있음. 지워진 상품은 주문 확정에서 DB 가 막는다 | 같음 |
| 좋아요 수 | 최대 TTL 60초 오래될 수 있음. 누른 직후 화면은 좋아요 응답의 `likeCount` 로 갱신한다(기존 계약). TTL 안에 새로고침하면 숫자가 어긋날 수 있다 | 같음 |
| 주문 금액 · 재고 · 포인트 판단 | 캐시를 쓰지 않고 DB 를 따른다 | 같음 |

## 7. 검증 계획

| 장면 | 확인할 결과 |
|---|---|
| 같은 입력의 miss · hit | 결과 일치, hit 에서 SQL 0회 |
| 없는 상품 · 삭제된 상품 | 404, 두 번째 요청은 SQL 0회 |
| 없는 ID 조회 뒤 그 ID 로 상품 생성 | 생성 뒤 조회가 200 |
| 가격 수정 · 상품 삭제 commit 뒤 재조회 | 새 값 · 404, 다른 상품 캐시는 유지 |
| 재고 변경 · 주문 확정 | 품절이 뒤집힐 때만 무효화 |
| 좋아요 · 브랜드 수정 · 브랜드 삭제 | 무효화하지 않음 |
| DB 변경 rollback | 버전이 오르지 않음 |
| 모든 쓰기 경로 | 3.2 표대로 무효화를 부르는지 |
| 늦은 채움 | 래치로 "이전 조회의 DB 읽기 → 변경 commit · 버전 증가 → 이전 조회의 저장 → 새 조회" 를 만들고 새 조회가 최신인지 |
| `INCR` 실패 · Redis 무응답 | 쓰기는 성공하고 재처리 뒤 최신 반영 / 대기 한도 안에 DB 결과 반환 |

## 8. 측정 계획

- MockMvc 기준 상세 요청의 지연을 **DB 만 · C · C + Lua** 로 비교했다. 비교할 때 Lua 읽기는 실험 코드에만 두고 포트 구현을 바꿔 끼웠다. 회차마다 세 방식의 순서를 돌려 쟀다.
- **결과 (`product-detail-cache.md`):** p50 기준 DB 만 약 2.9~3.4ms, C hit 약 0.9~1.1ms, C + Lua hit 약 0.6~0.7ms. Lua 는 C 보다 약 0.35~0.42ms(C hit 의 약 35~40%) 짧다. 이 결과로 C + Lua 를 채택했다(3.1).
- 전환 뒤 실험은 **DB 만 · 제품 캐시 hit** 두 방식을 비교한다.
- 동시 miss(스템피드)는 대책 없이 시작해 쟀다(`cache-stampede.md`). 동시 요청이 거의 모두 원본으로 가서, 데이터 키마다 원본 조회를 한 번으로 모으는 대책을 더했다(`stampede-design.md`).

## 9. 한계

- **스크립트가 데이터 키를 KEYS 로 받지 않고 안에서 만든다.** 지금 구성(master-replica)에서는 문제가 없지만, Redis Cluster 로 옮기면 버전 키와 데이터 키를 같은 슬롯에 두는 해시 태그(`{productId}`)를 붙이고 키를 KEYS 로 넘기도록 바꿔야 한다.
- **인기 상품의 버전 키에 master 읽기가 몰린다(핫 키).** C 와 C + Lua 모두 같다. 문제가 되면 앱 메모리의 짧은 캐시(가격 · 품절 최신성 완화)나 버전을 replica 에서 읽기(복제 지연 동안 옛 값)를 검토한다.
- 버전 키가 무효화된 상품 수만큼 TTL 없이 남는다.
- 서로 다른 없는 ID 로 오는 요청(크롤링 · 무작위 ID)은 "없음" 캐시로 막지 못하고, 그 키가 쌓인다. 요청량 제한이나 존재하는 ID 집합(블룸 필터 등)이 필요하며 이번 범위 밖이다.
- 무효화 실패 기록은 앱 메모리라 재시작하면 사라진다(최대 TTL 동안 오래된 값).
- 버전이 오른 직후 인기 상품의 동시 miss 는 원본 1번으로 모은다(`stampede-design.md`). 다만 무효화 뒤 첫 1번은 원본을 읽는다.
