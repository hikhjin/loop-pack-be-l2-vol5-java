# 캐시 스템피드 측정

인기 키의 캐시가 사라진 직후 동시 요청이 몰릴 때 원본 DB 조회가 몇 번 일어나는지 쟀다(`detail-cache-design.md` 8). 목록 · 상세 캐시에는 동시 miss 대책이 없다(`cache-design.md` 8, `detail-cache-design.md` 9). 대책을 둘지, 둔다면 무엇을 둘지 정하는 근거로 썼다. 대책을 넣은 뒤의 재측정은 5절이다.

- 실험 코드: `CacheStampedeExperiment` (`RUN_EXPERIMENT=true`)
- 실행일: 2026-10-18, MySQL 8.0 · Redis 7.0 단일 노드 Testcontainers, **두 번 실행**
- 데이터: `seed/week4-product-seed.sql` (상품 1만 개)

## 1. 측정 방법

- **한 시행:** 그 키를 무효화(버전 올림)한 뒤, N 개 스레드가 출발 신호를 함께 받아 같은 요청을 한 번씩 보낸다. 요청이 한순간에 몰리는, **가장 나쁜 경우**다.
- **원본 조회 수:** Hibernate 가 준비한 SQL 수를 원본 한 번의 SQL 수(상세 1개, 목록 2개)로 나눈다. 측정 전에 "무효화 뒤 첫 요청은 원본 한 번, 다음 요청은 SQL 0개"인지 확인했다.
- **요청 지연:** 출발 신호부터 그 요청이 끝날 때까지. Facade 를 직접 부른다(MockMvc · 톰캣 제외).
- 장면: 인기 상품(좋아요 250) 상세, 전체 목록 좋아요순. N = 1, 10, 50, 100. 준비 3회 뒤 20회 시행.
- **테스트 커넥션 풀은 10개다.** 원본을 읽는 요청은 커넥션을 기다릴 수 있다. 연결 대기 한도는 3초다.

## 3. 관찰

1. **한순간에 몰린 요청은 거의 모두 원본으로 갔다.** N 이 10 · 50 이면 시행마다 정확히 N 번, 100 이면 69~100 번이다. 모든 요청이 첫 원본 조회가 캐시에 저장되기(수 ms) 전에 캐시를 확인하므로 모두 miss 다. N=100 에서 일부가 원본을 피한 것은 늦게 출발한 스레드가 저장 뒤에 캐시를 읽었기 때문으로 본다.
2. **원본이 늘어나는 만큼 지연이 늘었다.** 커넥션이 10개라, 원본을 읽는 요청은 커넥션 앞에서 줄을 선다. N=100 에서 p50 이 N=1 의 약 6~15배, 최대 220ms 다. 같은 결과를 위해 원본 조회를 100번 한 것이다.
3. **실패는 없었다.** 원본 한 번이 수 ms 라, 100건이 줄을 서도 연결 대기 한도(3초)에 닿지 않았다. 원본이 더 무겁거나 동시 요청이 더 많으면 대기 한도를 넘는 실패가 생길 수 있다(재지 않음).
4. **원본이 무거울수록 같은 N 에서 더 오래 걸렸다.** N=100 의 p50 은 상세 약 36~40ms, 목록 약 54~89ms 다. 목록은 원본 한 번에 SQL 이 2개다.
5. **스템피드는 원본 시간을 늘려 스스로를 키운다.** 실제 요청은 한순간이 아니라 시간에 퍼져 들어온다. 이때 원본으로 가는 요청 수는 "초당 요청 수 × (원본이 저장되기까지의 시간)" 이다. 그런데 원본 조회가 몰리면 커넥션 대기로 그 시간이 길어지고(관찰 2), 그동안 들어온 요청도 miss 가 된다.
6. **N=1 의 목록 원본(약 5.5~6.3ms)이 목록 측정의 DB 만 값(전체 · likes_desc 약 24ms, `product-query-cache.md`)보다 훨씬 짧다.** 이 실험은 Facade 직접 호출이고 목록 측정은 MockMvc 다. 그 차이만으로는 설명되지 않을 만큼 커서, 원인은 확인하지 않았다. 이 문서의 결론(동시 요청이 모두 원본으로 간다)에는 영향이 없다.

## 4. 대책 후보 (대책 전에 정리)

| 후보 | 원본 조회 수 (인스턴스 M 대) | 얻는 것 | 포기하는 것 |
|---|---|---|---|
| 대책 없음 (지금) | 몰린 요청 수만큼 | 구현 없음 | 측정처럼 원본이 몰려 지연이 늘고, 원본이 무거우면 커넥션 대기 실패가 생길 수 있다 |
| **앱 안에서 요청 합치기** (키별로 진행 중인 원본 조회 하나를 나머지가 기다려 결과를 같이 씀) | 최대 M 번 | Redis 왕복이 늘지 않고 구현이 짧다. 기다리는 요청은 커넥션을 잡지 않는다 | 인스턴스마다 한 번씩은 원본을 읽는다. 기다리는 동안 첫 요청이 실패하면 함께 실패하거나 다시 읽어야 한다 |
| Redis 락으로 한 요청만 채우기 (`SET NX PX`) | 1 번 | 여러 인스턴스를 합쳐도 원본 1번 | 기다리는 요청의 재시도 간격 · 횟수, 락 만료, 락을 쥔 요청의 실패 처리가 필요하다. miss 마다 Redis 왕복이 는다 |
| 만료 전에 미리 갱신 (확률적 조기 갱신 · 논리 만료) | TTL 만료 때만 줄어듦 | TTL 만료로 생기는 스템피드를 거의 없앤다 | **무효화로 생기는 miss 는 못 막는다.** 이번 장면(무효화 직후)이 그 경우다 |
| 무효화 뒤 옛 값을 잠시 내주며 한 요청만 갱신 (stale-while-revalidate) | 1 번 | 기다리는 요청이 없다 | 가격 · 품절을 옛 값으로 내준다. "변경 뒤 순차 조회는 최신"(`cache-design.md` 5, `detail-cache-design.md` 5)을 어긴다 |

- 이 프로젝트에서 키가 사라지는 경우는 대부분 **무효화**(가격 수정, 품절 전환, 상품 생성 · 삭제)다. TTL 만료만 다루는 대책은 이번 장면을 줄이지 못한다.
- 앱 안의 요청 합치기와 Redis 락은 함께 쓸 수도 있다. 앱 안에서 먼저 합치면 Redis 락을 다투는 요청이 인스턴스 수만큼으로 준다.

## 5. 대책 뒤 (앱 안 합치기 + Redis 락)

`stampede-design.md` 의 대책을 넣고 같은 실험을 두 번 다시 돌렸다. 실험 코드는 그대로다.

원본 조회 수는 두 실행 모두 시행 20회 전부 1번이었다(최소 = 평균 = 최대 = 1).

1. **동시 요청이 몇 개든 원본은 1번이다.** 대책 전에는 N 번(N=100 에서 69~100번)이었다.
2. **몰릴 때의 지연이 크게 줄었다.** N=100 p50 이 상세 약 36~40ms → 약 9~10ms, 목록 약 54~89ms → 약 11ms. 기다리는 요청은 커넥션 앞에 줄 서지 않고 첫 요청의 결과를 받는다.
3. **혼자 오는 miss(N=1)는 조금 느려졌다.** p50 약 5.5~6.3ms → 약 7.3~8.4ms. 락을 잡고 푸는 Redis 왕복 2번이 더해진 몫이다. 왕복 2번(이 환경에서 약 0.5ms)보다 늘어난 나머지는 나눠 재지 않았다. hit 경로는 바뀌지 않는다.
4. 이 실험은 서버 한 대라 원본 1번은 주로 앱 안 합치기의 결과다. 서버 두 대에서 1번인지는 `CacheLoadCoordinatorTest` 로 확인했다(측정 아님).

## 6. 한계

- 한순간에 몰리는 가장 나쁜 경우만 쟀다. 시간에 퍼져 들어오는 요청(초당 요청 수 기준)은 재지 않았다.
- 앱 인스턴스 하나, 커넥션 풀 10개, 같은 PC 의 컨테이너다. 운영 풀 크기(기본 설정 40개)에서는 줄 서는 정도가 달라진다.
- 두 번 실행했다. 관찰 6 의 목록 원본 비용 차이는 확인하지 않았다.
- 6절의 "대책 뒤"도 같은 조건(서버 한 대)이다.
