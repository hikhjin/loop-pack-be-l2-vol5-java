# 캐시 스템피드 대책 설계

목록 · 상세 캐시에서 같은 키의 동시 miss 가 모두 원본 DB 로 가는 문제(`cache-stampede.md`)를 줄인다. hit 경로(스크립트 한 번, `cache-design.md` 4.1)는 바꾸지 않고, **miss 뒤 원본을 읽는 단계**에만 끼어든다.

## 1. 목표와 가정

- **목표: 같은 키의 동시 miss 에서 원본 조회를 최대한 줄인다.** DB 조회는 커넥션 획득 · 트랜잭션 · 왕복 비용 때문에 캐시 hit 보다 약 3배 이상 느리고(`product-detail-cache.md`), 몰리면 커넥션 앞에 줄을 서서 더 느려진다(`cache-stampede.md` 관찰 2).
- **가정: 앱 서버는 여러 대다.** 서버 한 대 안에서만 합치면 서버 수만큼 원본을 읽는다.
- **원칙: 캐시 쪽 문제로 조회가 실패하지 않는다.** 기다리던 첫 요청이 실패하거나 대기 한도를 넘으면 각자 원본을 읽는다. 지금의 Redis 장애 우회(`cache-design.md` 4.2)와 같은 원칙이다.

## 2. 대책 선택

| 후보 | 판단 |
|---|---|
| 대책 없음 | 몰린 요청 수만큼 원본을 읽는다(측정에서 N 번) |
| 앱 안 요청 합치기만 | 서버 안에서는 1번이지만 서버 M 대면 M 번 |
| Redis 락만 | 서버를 합쳐 1번. 그러나 같은 서버 안의 요청도 모두 락을 다투고 Redis 를 반복 확인한다 |
| **앱 안 합치기 + Redis 락 (채택)** | 서버 안에서 먼저 합쳐 락을 다투는 요청이 서버당 1개로 준다. 서버를 합쳐 원본 1번 |
| 만료 전에 미리 갱신 (확률적 조기 갱신 · 논리 만료) | TTL 만료만 다룬다. 이 프로젝트에서 키가 사라지는 경우는 대부분 무효화(가격 수정, 품절 전환, 상품 생성 · 삭제)라 맞지 않는다 |
| 무효화 뒤 옛 값을 잠시 내주며 한 요청만 갱신 | 가격 · 품절을 옛 값으로 내준다. "변경 뒤 순차 조회는 최신"(`cache-design.md` 5, `detail-cache-design.md` 5)을 어긴다 |

## 3. 흐름

miss 를 확인한 요청(스크립트로 읽은 버전 v, 데이터 키 = `…:ver=v…`)부터 시작한다.

```
1. 앱 안 합치기 (키 = 데이터 키)
   ─ 같은 데이터 키를 이미 읽고 있는 요청이 있으면 그 결과를 기다린다
       ─ 성공하면 그 값을 쓴다
       ─ 실패했거나 대기 한도를 넘으면 → 원본 조회 (저장하지 않는다)
   ─ 없으면 이 요청이 앱 안의 첫 요청이 되어 2로

2. Redis 락 (키 = lock:{데이터 키}, 값 = 무작위 토큰)
   SET lock:… {토큰} NX PX {락 만료}
   ─ 잡음  → 원본 조회 → 데이터 키 저장(TTL) → 락 해제(토큰이 같을 때만 지움)
   ─ 못 잡음 → 다른 서버가 읽는 중. 확인 간격마다 데이터 키를 읽는다
                ─ 값이 생기면 그 값을 쓴다
                ─ 대기 한도를 넘으면 → 원본 조회 → 데이터 키 저장
   ─ Redis 오류 → 락 없이 원본 조회 → 저장 시도
```

- **락 키에 버전이 들어간다.** 데이터 키에서 만들기 때문이다. 무효화로 버전이 오르면 새 버전의 요청은 새 락을 쓰고, 옛 버전을 읽던 요청과 서로 기다리지 않는다. 늦은 채움이 옛 버전 키에만 들어가는 성질(`detail-cache-design.md` 3.1)도 그대로다.
- **원본이 비어 있는 결과("없음", 상세 3.3)도 같은 방식으로 합친다.** 저장된 "없음"도 값이 생긴 것으로 본다.
- **락 해제는 토큰을 비교해 지운다(Lua).** 락 만료 뒤 다른 서버가 새로 잡은 락을 지우지 않기 위해서다.
- **기다리는 요청은 DB 커넥션을 잡지 않는다.** 앱 안에서는 결과를 기다리고, 다른 서버를 기다릴 때는 Redis 만 읽는다. 원본은 트랜잭션이 없는 Facade 에서 부르는 loader 안에서 읽으므로(`cache-design.md` 4.1), 기다리는 동안 열린 트랜잭션도 없다.
- **앱 안 합치기의 첫 요청이 실패하면 기다리던 요청은 각자 원본을 읽되 저장하지 않는다.** 첫 요청의 실패가 원본 오류라면 같은 오류를 각자 다시 겪고 그대로 나간다(원본 오류는 감싸지 않는다, `cache-design.md` 4.2). 저장을 생략하는 이유는 같은 키에 저장이 겹치는 것을 줄이기 위해서이며, 겹쳐도 같은 버전 · 같은 원본이라 결과는 같다.

## 4. 값

설정 키(`product-cache.load-lock.*`)의 기본값으로 둔다. 목록 · 상세 캐시의 TTL 처럼 코드의 기본값을 쓰고, 테스트는 값을 줄여 확인한다.

| 값 | 기본 | 근거 | 대가 |
|---|---|---|---|
| 락 만료 `ttl-ms` | 3,000 | 원본 조회는 커넥션 대기 한도(3초) 안에 끝나거나 실패한다 | 락을 쥔 서버가 죽으면 다른 서버는 최대 3초 기다린 뒤 각자 읽는다 |
| 대기 한도 `wait-ms` | 3,000 | 정상인 첫 요청은 이 안에 끝난다. 더 짧으면 정상적으로 느린 원본을 기다리다 각자 읽어 조회 수가 다시 는다 | DB 가 아주 느릴 때 사용자가 최대 3초 기다린다 |
| 확인 간격 `poll-ms` | 10 | 원본 조회가 수 ms 라, 다른 서버를 기다리는 요청의 추가 지연이 10ms 를 넘지 않는다 | 기다리는 요청 하나가 Redis 에 초당 최대 100번 읽기를 보낸다(서버당 1개) |

## 5. 구현 위치

| 책임 | 위치 |
|---|---|
| 앱 안 합치기 + Redis 락 + 대기 · 우회 (목록 · 상세 공용) | `infrastructure/product/CacheLoadCoordinator` |
| miss 경로에서 coordinator 사용 | `RedisProductListCache`, `RedisProductDetailCache` |
| 값 | `CacheLoadCoordinator` 의 설정 기본값 (`product-cache.load-lock.*`) |

- 도메인 포트(`ProductListCache`, `ProductDetailCache`)의 약속은 바뀌지 않는다. "loader 의 오류는 그대로 나간다", "캐시 저장소 오류는 원본 결과로 대신한다"도 그대로다.

## 6. 검증 계획

| 장면 | 확인할 결과 |
|---|---|
| 한 coordinator 에 같은 키로 동시 N 개 | 원본 1번, 모두 같은 값 |
| 서로 다른 coordinator 둘(서버 두 대 흉내)이 같은 Redis 로 같은 키에 동시에 | 원본 1번 |
| 앱 안 첫 요청의 원본이 실패 | 첫 요청은 그 오류, 기다리던 요청은 각자 원본을 읽음 |
| 다른 서버가 락만 쥐고 값을 만들지 않음 (락 쥔 서버가 죽음) | 대기 한도 뒤 각자 원본을 읽고 저장 |
| 락 잡기에서 Redis 오류 | 락 없이 원본을 읽음 |
| 버전이 다른 데이터 키 | 서로 기다리지 않음 |
| 락 해제 | 내 토큰일 때만 지움 (만료 뒤 다른 서버가 잡은 락은 그대로) |
| 기존 목록 · 상세 캐시 테스트 | 그대로 통과 (늦은 채움, 장애 우회, 무효화 포함) |
| 스템피드 재측정 (`CacheStampedeExperiment`) | 같은 조건에서 원본 조회 수 · 지연을 대책 전과 비교 |

**결과 (`cache-stampede.md` 5절):** 같은 조건(무효화 직후 동시 N = 10 · 50 · 100)에서 모든 시행의 원본 조회가 1번이었다(대책 전 N 번). N=100 의 p50 은 상세 약 36~40ms → 약 9~10ms, 목록 약 54~89ms → 약 11ms. 대신 혼자 오는 miss(N=1)는 p50 이 약 6ms → 약 7~8ms 로 늘었다. 서버 두 대 장면은 측정이 아니라 `CacheLoadCoordinatorTest` 로 확인했다.

## 7. 한계

- **무효화 뒤 첫 1번은 원본을 읽는다.** 대책이 줄이는 것은 같은 키의 동시 miss 다.
- 락 쥔 서버가 죽거나 원본이 대기 한도보다 오래 걸리면 그 순간에는 각자 원본을 읽어 조회 수가 다시 는다.
- 다른 서버를 기다리는 요청은 확인 간격만큼 응답이 늦어질 수 있다(최대 약 10ms).
- 락 키도 데이터 키처럼 스크립트 밖에서 따로 다루므로, Redis Cluster 로 옮겨도 이 부분은 그대로 동작한다. 데이터 키를 스크립트 안에서 만드는 읽기 쪽의 제약(`cache-design.md` 8)은 그대로다.
- 서로 다른 키(예: 브랜드 목록 여러 개)가 한꺼번에 무효화되면 키마다 1번씩은 원본을 읽는다.
- **혼자 오는 miss 도 락 잡기 · 해제로 Redis 왕복이 2번 는다.** 측정에서 N=1 의 p50 이 약 1.5~2ms 늘었다. 왕복 2번(이 환경에서 약 0.5ms)보다 큰 나머지는 나눠 재지 않았다.
