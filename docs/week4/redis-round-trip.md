# 상품 상세 캐시 hit 의 Redis 왕복 측정

상세 캐시의 무효화 방식(A. 키 삭제 vs C. 상품별 버전)을 고르기 전에, C 가 hit 마다 더하는 왕복 1회의 비용을 따로 쟀다. 비교 기준은 상세 DB 원본 p50 약 2.8ms(`product-query-detail.md`)다.

- 실험 코드: `RedisRoundTripExperiment` (`RUN_EXPERIMENT=true`)
- 실행일: 2026-10-18, Redis 7.0 단일 노드 Testcontainers, **두 번 실행**
- 연결: 상품 캐시가 실제로 쓰는 `ProductCacheRedisConfig` 의 master · replica 우선 템플릿. 단일 노드라 둘이 같은 노드를 가리킨다
- 값: 상세 한 건 크기의 `ProductView` JSON 147 bytes. **역직렬화 · MockMvc 는 포함하지 않는다**

## 1. 측정 방법

| 방식 | 읽는 순서 | 왕복 |
|---|---|---|
| A. 키 삭제 | 데이터 키 (replica 우선) | 1 |
| C. 상품별 버전 | 버전 키 (master) → 그 버전의 데이터 키 (replica 우선) | 2 |
| C 변형. Lua | 스크립트 안에서 버전을 읽고 그 버전의 데이터 키를 읽음 (master) | 1 |

- 회차마다 세 방식을 한 번씩 읽고, 회차마다 순서를 돌린다. 시간에 따른 흔들림이 한 방식에 몰리지 않게 하기 위해서다.
- 준비 2,000회차 뒤 10,000회차를 잰다.
- 측정 전에 세 방식 모두 같은 JSON 을 돌려주는지 확인했다.

## 2. 결과 (ms)

| 방식 | 실행 | 평균 | p50 | p95 | p99 | 최대 |
|---|---|---|---|---|---|---|
| A. 키 삭제 | 1 | 0.255 | 0.229 | 0.407 | 0.792 | 17.2 |
| | 2 | 0.296 | 0.238 | 0.577 | 1.329 | 13.1 |
| C. 상품별 버전 | 1 | 0.518 | **0.459** | 0.821 | 1.434 | 77.2 |
| | 2 | 0.605 | **0.477** | 1.139 | 2.598 | 85.1 |
| C 변형. Lua | 1 | 0.266 | 0.238 | 0.428 | 0.809 | 8.1 |
| | 2 | 0.335 | 0.248 | 0.590 | 1.372 | 97.3 |

## 3. 관찰

1. **왕복 1회는 이 환경에서 p50 약 0.23~0.24ms다.** C 는 A 의 거의 정확히 두 배(p50 약 0.46~0.48ms)로, 늘어난 비용은 왕복 하나만큼이다. p95 · p99 도 대략 두 배다.
2. **늘어난 0.23ms 는 상세 DB 원본(p50 약 2.8ms)의 약 8% 다.** 상세 hit 의 나머지 비용(MockMvc · 역직렬화 · 응답 직렬화)은 이번에 재지 않았다. 목록 hit(왕복 2회 포함, 약 0.8~1.9ms, `product-query-cache.md`)로 보면 C 의 상세 hit 도 원본보다 충분히 짧을 것으로 추정한다(미측정).
3. **Lua 변형은 왕복이 1회라 A 와 지연이 같다.** C 의 "늦은 채움이 옛 버전 키에만 들어간다"는 성질을 A 의 지연으로 얻는다. 대가는 다음과 같다.
   - 스크립트를 따로 관리하고, 목록 캐시 구현(버전 · 데이터를 따로 읽음)과 방식이 달라진다.
   - 데이터 키를 스크립트 안에서 만들어서, Redis Cluster 로 가면 두 키를 같은 슬롯에 두는 해시 태그(`{97}`)가 필요하다.
   - master 에서만 읽어서 replica 로 읽기를 나누지 못한다.
4. **최대값(8~97ms)은 1만 표본 중 몇 건의 튐이라 해석하지 않는다.** 방식과 관계없이 나타났고, 실행마다 어느 방식에 나올지 달랐다. GC 나 Docker 쪽 지연으로 추정한다(나눠 재지 않음).

## 4. 한계

- **같은 PC 의 컨테이너라 실제 운영보다 왕복이 짧다.** 운영에서 앱과 Redis 가 다른 서버라면 왕복이 더 길어진다. 그래도 C 가 더하는 비용은 "왕복 1회"로 같으므로, 운영에서는 그 환경의 Redis 왕복 시간을 그대로 더해 판단하면 된다.
- replica 가 없어 master · replica 를 실제로 나눠 읽는 비용 차이는 재지 않았다.
- 한 스레드에서 차례로 읽은 값이다. 동시 요청이 많을 때의 지연은 재지 않았다.
