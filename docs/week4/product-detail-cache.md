# 상품 상세 캐시 hit 측정 (MockMvc)

`detail-cache-design.md` 8절의 측정이다. 상세 요청 한 건의 지연을 **DB 만 · C(상품별 버전, 왕복 2회) · C + Lua(왕복 1회)** 로 비교해, 3.1 의 C / C + Lua 를 다시 판단하는 근거로 쓴다.

- 실험 코드: `ProductDetailCacheExperiment` (`RUN_EXPERIMENT=true`). 2절은 실험 전용 Lua 변형(`LuaProductDetailCache`, 전환 뒤 지움)으로 잰 값이다
- 실행일: 2026-10-18, MySQL 8.0 · Redis 7.0 단일 노드 Testcontainers, **두 번 실행**
- 요청: `GET /api/v1/products/{id}`. MockMvc 로 한 스레드에서 차례로 요청. 네트워크 · 톰캣은 포함하지 않음

## 1. 측정 방법

- 포트(`ProductDetailCache`)를 바꿔 끼우는 구현을 `@Primary` 로 두고, **같은 컨텍스트에서 방식만 바꿔** 같은 요청을 보낸다. C 는 제품 코드(`RedisProductDetailCache`), Lua 는 키 · 저장 형식이 같고 읽기만 스크립트 한 번으로 바꾼 변형이다.
- 측정 전에 세 방식의 응답 본문이 같은지, 요청당 SQL 이 DB 만 1개 · C 와 Lua 의 hit 0개인지 확인했다.
- 회차마다 세 방식을 한 번씩, 회차마다 순서를 돌려 잰다. 준비 500회차 뒤 3,000회차.

## 2. 결과 (ms)

| 방식 | Redis 왕복 | 요청당 SQL | 실행 | 평균 | p50 | p95 | p99 |
|---|---|---|---|---|---|---|---|
| DB 만 (캐시 없음) | 0 | 1 | 1 | 4.482 | 3.378 | 9.389 | 19.545 |
| | | | 2 | 3.262 | 2.929 | 5.264 | 9.834 |
| C. 상품별 버전 hit | 2 | 0 | 1 | 1.464 | **1.082** | 3.336 | 7.738 |
| | | | 2 | 1.053 | **0.933** | 1.710 | 3.215 |
| C + Lua hit | 1 | 0 | 1 | 0.914 | **0.666** | 2.110 | 4.993 |
| | | | 2 | 0.664 | **0.583** | 1.049 | 2.353 |

최대값(7~178ms)은 3,000 표본 중 몇 건의 튐이라 표에서 빼고 해석하지 않는다. 실험 결과 파일(`build/experiment/product-detail-cache.md`)에는 남아 있다.

## 3. 관찰

1. **C hit 는 DB 만보다 p50 이 약 3배 짧다** (약 2.9~3.4ms → 약 0.9~1.1ms). 앞선 추정(`product-query-cache.md` 관찰 4, "약 2.8ms → 약 1ms")과 맞는다. p95 · p99 도 2.5~3배 짧다.
2. **Lua 는 C 보다 p50 이 약 0.35~0.42ms 짧다. C hit 시간의 약 35~40% 다.** 절대값은 작지만 hit 끼리의 비율로는 작지 않다.
3. **이 차이는 Redis 왕복만 따로 잰 값(약 0.23ms, `redis-round-trip.md`)보다 크다.** 원인은 나눠 재지 않았다. 두 측정의 C 는 같은 연결 구성(버전은 master 연결, 데이터는 replica 우선 연결)이라 연결 구성의 차이는 아니다. MockMvc 경로에서 흔들림이 커진 것으로 추정할 뿐, 확인하지 않았다.
4. **DB 만의 실행 간 차이(p50 3.4 vs 2.9ms)가 캐시 쪽보다 크다.** 캐시 hit 는 커넥션 · 트랜잭션을 거치지 않아 흔들림도 작다.

## 4. 판단에 쓰는 법

| 선택 | 이 측정이 보여 주는 것 | 남는 대가 (`detail-cache-design.md` 3.1, 9) |
|---|---|---|
| C 유지 | DB 만 대비 약 3배. 목록 캐시와 같은 구조 | hit 마다 Lua 보다 약 0.4ms 더 걸림 |
| C + Lua 로 전환 | C 대비 hit 약 35~40% 더 짧음 | 스크립트 관리, 목록 구현과 방식이 달라짐, Cluster 전환 시 해시 태그, 버전 · 데이터 모두 master 에서 읽음. 제품 코드로 옮기려면 C 의 장애 처리(Redis 오류 → DB 우회)와 그 테스트를 Lua 쪽에도 갖춰야 함 |

master 요청 수는 두 방식이 같다(hit 마다 1회). 인기 상품 버전 키에 master 읽기가 몰리는 문제는 어느 쪽이든 남는다.

## 5. 전환 뒤 확인 (C + Lua 채택)

4절을 근거로 C + Lua 를 채택해 제품 코드(`RedisProductDetailCache` + `VersionedCacheScript`)로 옮겼다. 실험 전용 변형(`LuaProductDetailCache`)은 지웠고, 실험은 **DB 만 · 제품 캐시 hit** 두 방식을 비교하도록 바꿨다. 한 번 실행했다.

| 방식 | Redis 왕복 | 요청당 SQL | 평균 | p50 | p95 | p99 |
|---|---|---|---|---|---|---|
| DB 만 (캐시 없음) | 0 | 1 | 3.643 | 3.032 | 6.711 | 11.797 |
| 제품 캐시 hit | 1 | 0 | 0.981 | **0.777** | 1.868 | 4.403 |

- DB 만 대비 p50 약 3.9배 짧다. 응답 본문은 두 방식이 같고 hit 의 SQL 은 0개였다.
- p50 0.78ms 는 2절의 실험용 Lua(약 0.58~0.67ms)보다 길고 C(약 0.93~1.08ms)보다 짧다. **다른 실행끼리의 비교라 이 차이는 해석하지 않는다.** C 와 Lua 의 차이는 한 실행 안에서 번갈아 잰 2절의 값으로 판단했다. 제품 코드는 실험용 변형에 장애 처리(예외를 잡아 DB 로 우회)만 더했고, hit 경로의 Redis 호출은 같다.

## 6. 한계

- 같은 PC 의 컨테이너라 Redis 왕복이 실제 운영보다 짧다. 운영에서 Redis 가 다른 서버면 C 의 추가 왕복 1회는 더 길어진다.
- 한 스레드의 순차 요청이다. 동시 요청 · 스템피드는 재지 않았다(`detail-cache-design.md` 8 의 다음 단계).
- 두 번 실행한 결과다. Lua 와 C 의 차이가 왕복 측정보다 큰 이유는 확인하지 않았다(관찰 3).
